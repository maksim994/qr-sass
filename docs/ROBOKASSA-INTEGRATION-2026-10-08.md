## Что реализовано

- `BILLING_PROVIDER=yookassa|robokassa`; по умолчанию сохраняется ЮKassa. Старые заказы получают `provider=yookassa`, их идентификаторы не меняются. Ключи ЮKassa и прежний webhook нужны для ранее созданных платежей.
- Оформление Robokassa через POST на официальную платёжную страницу. Цена, тариф и архивные условия берутся на сервере. Заказ записывается до передачи формы покупателю.
- `Receipt` содержит конкретный тариф QR-S.ru, месяц доступа, количество 1 и полную сумму без НДС. Система налогообложения берётся из настроек магазина. URL-кодированный `Receipt` включён в подпись и передаётся внутри POST-формы; email покупателя передаётся отдельно.
- ResultURL проверяет пароль №2 выбранного по сохранённому заказу режима, алгоритм, сумму до копейки, идентификатор счёта, локальный заказ и подписанный `Shp_test`. Отбрасываются повторяющиеся параметры, неверные подписи, неподходящие тела и тела свыше 16 KiB.
- Начисление оплаченного месяца использует прежнюю транзакцию и блокировку кабинета. Повторное и параллельное уведомления не продлевают доступ повторно. Задержанное подтверждение отменённого заказа обрабатывается, возврат не возобновляется.
- Тестовый заказ подтверждается в истории, но не меняет подписку и не создаёт конверсию реальной оплаты или уведомление о выручке.
- Возврат покупателя на сайт ничего не подтверждает и не отменяет. Кабинет показывает сохранённый статус заказа своего workspace, автоматически обновляя ожидающий статус до 30 секунд.

## Настройки магазина

Личный кабинет → Мои магазины → нужный магазин → Технические настройки.

| Поле Robokassa | Переменная окружения |
| --- | --- |
| Идентификатор магазина | `ROBOKASSA_MERCHANT_LOGIN` |
| Алгоритм расчёта контрольной суммы | `ROBOKASSA_HASH_ALGORITHM` — `MD5`, `SHA256` или `SHA512`, точно как в кабинете |
| Тестовый пароль №1 | `ROBOKASSA_TEST_PASSWORD1` |
| Тестовый пароль №2 | `ROBOKASSA_TEST_PASSWORD2` |
| Основной пароль №1 | `ROBOKASSA_PASSWORD1` |
| Основной пароль №2 | `ROBOKASSA_PASSWORD2` |

Тестовый режим: `ROBOKASSA_TEST_MODE=true`; боевой: `false`. Основные и тестовые пароли должны различаться. Боевые ключи не нужны для локальных синтетических проверок. Реальные секреты хранятся в окружении, не в Git и не в переписке.

Создан приватный, исключённый из Git файл `.env.robokassa.local` с правами 0600. Он не загружается Next.js автоматически: значения нужно перенести в окружение выбранного тестового сервера или его приватный `.env.local`. Не копировать настройки синтетической базы в production.

Адреса для домена production после публикации кода:

| Поле | Адрес | Метод |
| --- | --- | --- |
| ResultURL | `https://qr-s.ru/api/billing/webhook/robokassa` | POST |
| SuccessURL | `https://qr-s.ru/api/billing/robokassa/return` | GET |
| FailURL | `https://qr-s.ru/api/billing/robokassa/return` | GET |

Для отдельного тестового окружения заменить домен во всех адресах и в `APP_URL`. Локальный localhost недоступен Robokassa. SuccessURL и FailURL одинаковы намеренно: итог берётся из базы, а не из адреса возврата. Новые адреса пока не опубликованы на qr-s.ru.

- Все 154 теста проходят, включая подписи, кодирование чека, диапазон InvId, сумму, режим, дубликаты параметров и неправильные ключи.
- ESLint и TypeScript проходят; production-сборка Next.js успешна.
- `scripts/verify-robokassa-integration.ts`: 9 проверок на отдельной PostgreSQL, включая добавочную повторяемую миграцию с существующими платежами и QR, 8 параллельных уведомлений, повтор, позднее подтверждение, возврат, изоляцию тестов, защиту от смешивания провайдеров и неизменность QR.
- `scripts/verify-robokassa-http.ts`: 6 проверок собранного приложения — права/CSRF, серверная цена и чек, ограничения callback, безопасный возврат, GET/POST подтверждения и отображение статуса в кабинете.

Оба интеграционных скрипта допускают только локальную базу с именем `qr_robokassa_test`; они создают синтетические записи. HTTP-проверка ожидает собранное приложение на `http://localhost:3105`, режим Robokassa test, магазин `isolated-shop`, SHA256, ключи `synthetic-test-one` / `synthetic-test-two` и JWT `synthetic-build-jwt-secret-at-least-32-characters`. Это публичные тестовые значения, не секреты магазина.

## Что осталось до запуска

1. Заполнить технические настройки и проверить фактическую активность Робочеков СМЗ.
2. Пройти реальную тестовую форму магазина на доступном извне тестовом окружении: состав покупки на форме, успешное уведомление, повтор, отказ и возврат в кабинет. Синтетические проверки не заменяют обмен с Robokassa.
3. Публиковать по `DEPLOY.md` и `docs/QR-COMPATIBILITY.md`: backup PostgreSQL/S3, проверка восстановления и миграции на копии production, baseline QR, сохранение образа для отката, проверка после релиза. Production-база в локальных проверках не использовалась.
4. После тестов переключить новые оплаты на Robokassa в боевом режиме, сохранив старые ключи ЮKassa. Выполнить согласованную реальную оплату и проверить чек у покупателя и в «Моём налоге», затем возврат и аннулирование чека. Автоматизация возвратов в эту интеграцию не входит.

Сверка старых платежей ЮKassa сохранена. Для Robokassa подтверждение сейчас приходит только через ResultURL: при пропущенном уведомлении требуется его повторная отправка из кабинета Robokassa или обращение в поддержку. Автоматическое восстановление через OpStateExt не добавлено; этот API не поддерживает тестовые платежи. Переход на FailURL не отменяет заказ, поэтому неподтверждённая попытка может остаться PENDING.

Откат новых checkout: `BILLING_PROVIDER=yookassa`. Добавочное поле БД совместимо с предыдущим приложением; его удалять не нужно. Пока существуют ожидающие заказы Robokassa, следует сохранять их callback и соответствующие ключи: откат самого приложения на старый код отключит новый маршрут.
