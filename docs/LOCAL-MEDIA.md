# Локальные медиа и независимая резервная копия

Основной backend — `MEDIA_STORAGE=local`, корень `MEDIA_ROOT=/data/media`. В Compose
`MEDIA_HOST_PATH` — каталог отдельного диска на хосте, смонтированный в `/data/media`.
Диск подключается до запуска Compose; `media-init` выдаёт права на корень UID/GID 1001.
Используйте выделенный каталог. Файлы переживают пересборку приложения.
Для разработки задайте доступный абсолютный `MEDIA_ROOT`. S3-ключи для local не нужны.

Все загрузки используют интерфейс `MediaStorage` через совместимый фасад `src/lib/s3.ts`.
S3 остаётся опциональным основным backend: `MEDIA_STORAGE=s3` и прежние `S3_*`.
Автоматических сетевых запросов к старому S3 в режиме local нет.

## Доступ

- Блог: `/media/blog/covers/...`, `/media/blog/content/...`.
- Аватары/favicon: `/media/assets/avatars/<user>/<file>`, `/media/assets/site/favicon_<id>.<ext>`.
- PDF, логотипы, аудио, видео и изображения workspace: прежние защищённые
  `/api/upload/<id>/file` и маршруты QR с действующими проверками доступа.

Ключи workspace, БД и адреса QR не меняются. Публичные пути разрешают только указанные
растровые изображения/ICO. Traversal, symlinks и SVG запрещены. **Не открывайте весь
`/data/media` через nginx alias**: там есть приватные файлы. Выдача сейчас через приложение
с GET/HEAD, ETag и immutable cache. При замене публичной картинки создавайте новое имя.
Исторический namespace блога/аватаров/favicon — `qr`; оставляйте `S3_PREFIX=qr`.

## Блог из папки копий

Файл копии: `md5(точный старый URL).slice(0, 10) + '.webp'`, нижний регистр.
Query/hash хэшируются вместе с URL. Проверяется реальный WebP, размер до 10 МБ,
коллизии и несовпадающие целевые файлы; пустая/ошибочная папка не принимается.

Задайте `MEDIA_COPIES_PATH` на хосте; папка монтируется read-only в `/copies`.
Перед production-изменениями выполните backup/baseline из `DEPLOY.md` и проверьте
процедуру на отдельной восстановленной БД. Команды для подготовленного окружения:

```bash
docker compose run --rm media-tools npm run media:migrate-blog -- \
  --copies /copies --dry-run --report /data/media/.blog-media-plan.json

docker compose run --rm media-tools npm run media:migrate-blog -- \
  --copies /copies --apply --report /data/media/.blog-media-applied.json
```

Без `--apply` БД и медиа не изменяются, создаётся только указанный отчёт. Apply требует
новый путь отчёта: оригинальные записи сохраняются до изменений с правами `0600`.
Сохраните отчёт также отдельно от диска медиа. Скрытые файлы не выдаются по HTTP
и исключены из backup медиа. Обычный Node: `npm run media:migrate-blog -- ...`
с переменными БД/`MEDIA_ROOT`; для `.env` запускайте `node --env-file=.env` перед TS-аргументами.

Результат: `/data/media/qr/blog/content/<hash>.webp`, адрес
`${APP_URL}/media/blog/content/<hash>.webp`. Старые одноимённые адреса на домене приложения
также читают копию по MD5 исходного URL без сетевых запросов (для URL без query).
Уже импортированные файлы с исходным ключом используются без повторного переименования.

Отсутствующая копия: удаляются img/Markdown image, пустые обёртки и одиночный figure
с подписью; обложка обнуляется, битые кандидаты srcset и изображения JSON-LD убираются.
Консоль и `missingArticles` отчёта содержат ID, slug, заголовок и отсутствующие URL.
Другие домены, проза, обычные ссылки и примеры кода остаются. Inline и reference
Markdown images поддерживаются, исходные reference definitions сохраняются.

Обрабатываются статьи/черновики, кэш HTML, `legacyHtml`, обложки, JSON-LD, `BlogImage`
и ожидающие правки. Даты публикации/редакционного обновления сохраняются, `updatedAt`
и история версий фиксируют техническое изменение. CAS-проверки защищают параллельные
правки. При конфликте вся транзакция БД откатывается; скопированные файлы остаются
для повтора. Повторный запуск без новых изменений не создаёт версии.
Исторические `BlogRevision` сохраняются неизменными: после восстановления старой
редакции повторите миграцию, чтобы снова убрать отсутствующие изображения.

## Старые пользовательские файлы

Папка WebP блога не восстанавливает пользовательские PDF, видео, аватары и логотипы.
Их нужно перенести с прежними ключами: `/data/media/<UploadedFile.key>`.
Если исходный S3 работает, доступен импорт всего namespace `qr/`:

```bash
docker compose run --rm media-tools npm run media:import-s3 -- \
  --report /data/media/.s3-import-plan.json
docker compose run --rm media-tools npm run media:import-s3 -- \
  --apply --report /data/media/.s3-import-applied.json
```

Источник — прежние `S3_*`. Импорт не удаляет/не перезаписывает локальные файлы,
затем меняет S3-адреса аватаров/favicon на локальные. Внешние OAuth-аватары сохраняются.
Для уже восстановленного дерева добавьте `--local-only`: проверяются только файлы
на диске и меняются адреса, S3 не вызывается. При отсутствии известных пользовательских
файлов apply останавливается со списком `missing`. Решение о переключении с такими
потерями требует отдельного разбора восстановления.

При переходе с доступного S3 оставляйте старое приложение на `MEDIA_STORAGE=s3` до
проверки импорта. На финальный импорт приостановите загрузки/редактуру, чтобы не
пропустить новые файлы после листинга. Затем переключайте на local и проверьте
старые QR/`verify-qr-health`, блог, аватары/favicon и приватный файл. Откат backend
на S3 после новых локальных загрузок требует сначала перенести новые файлы обратно.

## Ежедневная копия

Сервис `media-backup` запускается вместе с приложением. Укажите четыре параметра:

```dotenv
MEDIA_BACKUP_S3_ENDPOINT=https://s3.other-provider.example
MEDIA_BACKUP_S3_BUCKET=qr-media-backup
MEDIA_BACKUP_S3_ACCESS_KEY=...
MEDIA_BACKUP_S3_SECRET_KEY=...
MEDIA_BACKUP_S3_REGION=us-east-1
```

Все четыре пустые — сервис пишет `disabled` и ждёт, копий нет. Неполная конфигурация —
ошибка. HTTP, известные домены Beget, `s3.mvmolkov.ru` и текущий `S3_ENDPOINT` запрещены.
Для собственного домена отдельно проверьте, что backend действительно у другого
провайдера. Backup-ключи передаются только backup-сервису, приложение их не получает.

После настройки пересоздайте сервис штатным способом. Первая копия сразу, следующие
через 24 часа после успеха. Ошибка повторяется через час, не обновляя отметку успеха.
Healthcheck становится unhealthy при отсутствии копии/возрасте последнего успеха
старше 26 часов. Логи: время, скопированные/неизменённые файлы, без credentials.
Сам healthcheck уведомления не отправляет.

Сохраняются исходные ключи, MIME и SHA-256 в metadata. Неизменённые файлы пропускаются,
локальное удаление не удаляет объект в backup. Используйте отдельный приватный bucket
с versioning, сроком хранения старых версий и ключами без права удаления. Начальный
bucket пустой либо содержит только копию этого дерева. Mount backup-сервиса read-only.
Это копия медиа; PostgreSQL резервируется отдельно.

Однократная проверка с параметрами backup-сервиса:

```bash
docker compose run --rm media-backup node --experimental-strip-types \
  --import ./scripts/register-src-alias.mjs scripts/media-backup.ts
docker compose logs --tail=50 media-backup
```

## Проверка восстановления

Клиентом S3 своего провайдера скачайте bucket в отдельный каталог, например
`/data/media-restore`, сохраняя ключи `qr/...`. Сравните SHA-256 с metadata `sha256`,
количество объектов и реальные файлы разных типов. Подключите каталог к изолированной
копии приложения/БД и откройте блог/аватары и старые QR с файлами. Versioning нужен,
если повреждённый локальный файл уже попал в следующую копию. Не восстанавливайте
приватные файлы в публичный webroot.

Проверки разработки: `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`.
Интеграционная проверка на отдельной БД `qr_media_test` с применёнными миграциями:

```bash
MEDIA_MIGRATION_ISOLATED_TEST=1 DATABASE_URL=postgresql://.../qr_media_test \
  node --experimental-strip-types --import ./scripts/register-src-alias.mjs \
  scripts/verify-local-media.mjs
```
