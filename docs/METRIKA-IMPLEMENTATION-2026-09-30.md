`qr_creation_started` может встретиться и на главной, и в редакторе одного пути: для анализа входа группировать по source и уникальным посетителям, не складывать достижения как число клиентов. В редакторе означает открытие, а не первое нажатие клавиши.
`qr_downloaded` не доказывает запись файла на диск: браузер не раскрывает завершение пользовательского сохранения.
`subscription_paid` запрещён на клиенте. Не создавать на его основе цель покупки.
Содержимое QR, целевые URL, email, токены и идентификаторы кабинета в параметры новых событий не передаются.

## Согласие и повторные события

До согласия действия не отправляются и не накапливаются. После согласия текущая видимая страница/секция может отправить просмотр; прежние действия не воспроизводятся.
Просмотры биллинга/редактора защищены от повторного эффекта React в пределах одного монтирования. Повторный настоящий визит может считаться снова.
Готовность объявляется после постановки init в очередь Метрики: события начального рендера не теряются из-за порядка эффектов.
Существующий механизм отказа и отзыва согласия сохранён.

## Продолжение: серверные конверсии и OG

Выполнено после первого этапа:

- Новая регистрация Яндекс помечается внутри транзакции создания пользователя. POST `/api/analytics/registration` атомарно погашает маркер только для текущей cookie-сессии и регистрации за последние 15 минут. Обычный вход/привязка аккаунта не создают маркер. Клиент обращается к endpoint после согласия и готовности Метрики. Повторные вкладки не получают второй маркер. Это at-most-once передача: потеря ответа или закрытие страницы между погашением и отправкой может потерять клиентскую цель; серверный учёт регистрации сохраняется.
- Checkout запрашивает ClientID через API Метрики с ограничением ожидания 500 мс. Без согласия/счётчика/ответа оплата продолжает работать без атрибуции. Сервер проверяет формат и совпадение номера счётчика с настройками сайта, сохраняет версию согласия и время получения. Идентификатор не добавляется в metadata YooKassa.
- `npm run analytics:deliver` запускает отдельный обработчик. Нужны production-окружение и серверный `METRIKA_OAUTH_TOKEN`. Без них он не отправляет данные. Само расписание пока не установлено.
- В CSV попадают только ClientId, фиксированная цель payment_succeeded, серверное paidAt, реальная сумма и валюта. Источник — SUCCEEDED и isTest=false. Клиентский возврат из виджета не используется.
- Атомарный переход PENDING → SENDING предотвращает одновременную отправку двумя обработчиками. После загрузки хранится ID и отдельно опрашивается статус до PROCESSED. Авторизационные ошибки и 429 можно повторить не раньше чем через 15 минут. Неоднозначный сетевой результат, 5xx и прерванный SENDING переводятся в REVIEW: до ручной сверки загрузок повторной отправки нет. Это не обещание exactly-once на стороне внешнего API.
- Платежи старше 21 дня без отправки исключаются; после обработки ClientID удаляется. Истёкшее окно атрибуции от последнего визита всё равно может мешать сопоставлению: статус загрузки не доказывает наличие цели в отчёте.
- При отказе от cookies клиент немедленно прекращает отправку и делает ограниченный по времени запрос отмены ещё не отправленных конверсий текущего пользователя. При недоступной сети серверный отзыв не гарантируется; уже переданные и находящиеся в отправке данные автоматически не отзываются.
- Восстановленный из YooKassa платёж, который не удалось записать при checkout, остаётся без ClientID. Выручка учитывается сервером, выдуманная атрибуция не добавляется.
