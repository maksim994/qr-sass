# QR API v1 — контракт для модуля 1С-Битрикс

Реализация в ветке `codex/qr-api-v1`, от ночного релиза `a4d6b13` и его отчёта `34308b7`. Production ещё не обновлён этим изменением. Машинный контракт — `GET /api/v1/openapi.json`, версия 1.5.0; прежний Article API полностью сохранён в объединённой схеме. `openapi.yaml` содержит ту же схему (JSON — допустимый YAML).

## Доступ и ключи

QR API доступен на Бесплатном, Про и Бизнесе. Это отдельный доступ от прежнего API кабинета (`qre_`, Бизнес) и Article API (`qrs_blog_`, редакционные полномочия). Старые ключи продолжают работать в своих API; новые ключи не принимаются прежними обработчиками.

Ключ QR API создаётся владельцем/администратором в `/dashboard/api-keys`. Префикс `qrs_api_`, 32 случайных байта, SHA-256 вместо исходного ключа в БД. Полный ключ показывается только при создании. До 20 действующих ключей на кабинет. Название 1–64 символа; набор разрешений выбирается явно:

- `qr:read`: список, карточка и изображения;
- `qr:write`: создание и смена назначения;
- `stats:read`: агрегированная статистика.

Только `Authorization: Bearer <ключ>`. Cookie, query-параметры и ключи других API не принимаются. Кабинет определяется ключом, `workspaceId` в теле не допускается. Ключ перестаёт работать после отзыва или потери владельцем ключа роли OWNER/ADMIN в кабинете. Отзыв не останавливает уже созданные QR.

60 запросов в минуту на ключ. Счётчик в PostgreSQL атомарен и общий для всех экземпляров приложения. Окно — календарная минута UTC, поэтому на границе минут возможны два соседних пакета. Заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining`; при 429 — `Retry-After` в секундах. Не прошедшие авторизацию/scopes запросы не расходуют квоту ключа.

Все ответы QR API и управления ключами закрыты от кеширования (`private, no-store`), включая ошибки и бинарные изображения. Страница ключей исключена из Метрики, VK, пользовательского head-кода; полный ключ дополнительно помечен `ym-hide-content`. Управление ключами использует сессию и существующую CSRF-защиту.

## Запросы

Базовый URL: `https://qr-s.ru`. Схема успеха `{ "ok": true, "data": ... }`; ошибка `{ "ok": false, "error": "русский текст", "code": "...", "details": ... }`. В таблице ниже `{id}` — ID QR, а не shortCode.

| Метод и путь | Разрешение | Результат |
| --- | --- | --- |
| `GET /api/v1/qr/key` | любой действующий ключ | Имя, кабинет, scopes, тариф, лимиты |
| `GET /api/v1/qr?limit=50&offset=0` | `qr:read` | Активные QR кабинета, до 100, `nextOffset` или null |
| `POST /api/v1/qr` | `qr:write` | Создать динамический URL QR, HTTP 201 |
| `GET /api/v1/qr/{id}` | `qr:read` | Карточка QR |
| `PATCH /api/v1/qr/{id}` | `qr:write` | Обновить `targetUrl` динамического URL QR |
| `GET /api/v1/qr/{id}/image` | `qr:read` | PNG или SVG |
| `GET /api/v1/qr/{id}/stats?from=2026-10-01&to=2026-10-22` | `stats:read` | Открытия по дням и устройствам |

Отсутствующий, чужой и архивный QR дают одинаковый 404. DTO QR содержит только `id`, `name`, `kind`, `contentType`, `shortCode`, `shortUrl`, `targetUrl`, `source`, `createdAt`, `updatedAt`. `shortUrl` заполнен для динамических URL; для иных типов — null. В DTO нет payload, паролей Wi-Fi, хешей доступа, IP, user agent и других полей посетителей. Список не требует scope статистики и не возвращает счётчики открытий.

### Создание динамической ссылки

```sh
curl 'https://qr-s.ru/api/v1/qr' \
  -H 'Authorization: Bearer YOUR_QRS_API_KEY' \
  -H 'Content-Type: application/json' \
  --data '{"name":"Товар 123","targetUrl":"https://example.com/catalog/123/","source":"bitrix_module"}'
```

`name`: 1–120 символов. `targetUrl`: HTTP(S), до 2048 символов, без логина/пароля в URL. `source`: `bitrix_module` для модуля, `api` по умолчанию. Источник хранится отдельно от данных посетителей и виден в административном списке QR. Произвольные поля и источники отклоняются.

Создаётся `DYNAMIC / URL`; `shortUrl` указывает на `/r/{shortCode}`. Смена `targetUrl` сохраняет ID, shortCode и encodedContent, записывает ревизию. Изменять назначение можно в пределах текущих прав кабинета, в том числе после перехода на Бесплатный. Создание использует общую транзакцию с блокировкой Workspace: два бесплатных динамических кода считаются вместе с созданными через интерфейс и другими интеграциями, а не отдельно на каждый ключ.

Обычные ссылки, текст, Wi-Fi и телефон модуль генерирует статически локально. Динамический текст/Wi-Fi/телефон и визитка не входят в QR API v1. API не меняет ограничения типов и не добавляет новые публичные маршруты для сканирования.

### Изображение

```text
GET /api/v1/qr/{id}/image?format=svg&size=600&foreground=%23111111&background=%23ffffff&errorCorrectionLevel=H
```

`format`: png (по умолчанию) или svg. `size`: 128–2048, по умолчанию 600. Цвета: #RRGGBB, `#` кодируется как `%23`. Коррекция L/M/Q/H, по умолчанию H. Quiet zone — 4 модуля. Низкий контраст отклоняется с 400. Экспорт использует штатный renderer и сохранённый encodedContent; внешний логотип не загружается. Проверяется доступность PNG/SVG в текущем тарифе.

### Статистика

`from`, `to` обязательны, YYYY-MM-DD, включительно по UTC. Период от 1 до 366 дней. Пустые дни присутствуют с count=0.

```json
{
  "ok": true,
  "data": {
    "from": "2026-10-20",
    "to": "2026-10-21",
    "timezone": "UTC",
    "total": 2,
    "byDay": [{"date":"2026-10-20","count":0},{"date":"2026-10-21","count":2}],
    "byDevice": [{"device":"desktop","count":1},{"device":"mobile","count":1}]
  }
}
```

Пример синтетический. Устройства: mobile, desktop, tablet, unknown. Считаются уже записанные ScanEvent, без отдельных визитов и данных посетителей. Получение статистики и изображений не открывает `/r` и не расходует сканы ограниченных QR.

## Подключение модуля

1. Проверить ключ через `GET /api/v1/qr/key`. Для полного режима нужны все три scope. Не писать ключ в HTML и логи; хранить и передавать с сервера Битрикса.
2. Создать динамическую ссылку с `source=bitrix_module`, сохранить `id` и `shortUrl` у элемента. При изменении URL товара использовать PATCH; картинку получить по тому же id.
3. Кешировать статистику; при ошибке показывать последние данные. HTTP timeout 5 с. Если POST прервался после отправки, проверить список перед повторным созданием: Idempotency-Key в v1 не реализован.
4. Ссылки регистрации из модуля: `/register?utm_source=bitrix_marketplace&utm_medium=module_settings` (либо module/module_upsell/marketplace_page по месту). Уже выпущенный first-touch сохраняет эти значения до регистрации, включая обычную навигацию; это покрыто тестом.

Коды ошибок: 400 VALIDATION_ERROR, 401 UNAUTHORIZED, 403 FORBIDDEN (scope или квота; для квоты details.code), 404 NOT_FOUND, 429 RATE_LIMITED, 500 INTERNAL_ERROR. При 401 запросить новый ключ у администратора; при 429 соблюдать Retry-After; при 403 проверить scope и тарифный лимит.

## Проверка и выпуск

```sh
npm ci
npm run prisma:generate
npm test
npm run lint
npx tsc --noEmit
# Для build требуется отдельный JWT_SECRET длиной от 32 символов.
npm run build
# Обновить зафиксированную объединённую OpenAPI-схему:
node --experimental-strip-types --import ./scripts/register-src-alias.mjs scripts/sync-public-openapi.mjs
```

HTTP-проверка `scripts/test-qr-api-http.mjs` запускается с `DATABASE_URL`, `JWT_SECRET`, `RELEASE_TEST_APP_URL` на локальной изолированной тестовой базе и приложении с той же конфигурацией. Скрипт отказывается работать с внешним hostname и БД без `test` в имени, создаёт синтетические кабинеты и удаляет их в finally. Он не запускает SMTP, платежи и workers.

Миграция `20261022120000_qr_api_v1` только добавляет nullable creationSource и новую таблицу ключей. В релизе обязательны backup/restore, проверка на восстановленной копии, baseline старых QR и сценарий отката из `docs/QR-COMPATIBILITY.md` и `DEPLOY.md`. Локальные синтетические тесты не заменяют production-репетицию.
